# 用 Claude Code 半年后，我的 MCP 与插件配置方法论

**先说结论**：Claude Code 的工具生态（MCP + 插件）和健身房办卡一个道理——装的时候都觉得有用，真正留在日常流程里的不到三分之一。我前后装过十几个，最后稳定使用的是 5 个 MCP 服务器和 9 个插件。

这篇文章不罗列安装命令（官方文档写得比我好），只回答三个问题：

1. 每个工具**在我的工作流里到底解决什么问题**；
2. 哪些工具之间存在**隐性依赖或功能重叠**；
3. 如果重来一次，**按什么顺序装最合理**。

先说背景，方便你对号入座：我的主要场景有两个——维护一个 Obsidian 知识库 + VitePress 个人网站（就是你现在看到的这个），以及一条半自动的论文阅读流水线。如果你也是"知识管理 + 轻量开发"型用户，这篇的参考价值最大。

---

## 一、MCP：判断标准是"能不能替代我动手"

MCP 的本质是给模型接外部工具。我的选型标准很朴素：**这件事如果 Claude 没有它就得我自己上手做，那它就值得装**。

### codegraph：代码探索的效率分水岭

这是我认为被严重低估的一个 MCP。它把代码库预建成知识图谱（符号、调用关系、影响面），查询是亚毫秒级的。

没有它之前，Claude 探索代码的方式是 grep → 读文件 → 再 grep，一个"这个函数谁调用"的问题要十几轮工具调用，上下文还被一堆无关文件内容污染。有了它，`codegraph_explore` 一次调用直接返回相关符号的源码和调用链，`codegraph_impact` 在重构前告诉你改动会波及谁。

**真实案例**：前阵子修这个网站的图片加载 bug，"wikilink 插件在哪把 `![[...]]` 转成什么"这个问题，一次调用就定位到了具体行。没有这个工具，同样的定位至少要翻五六个文件。

适合：任何需要 AI 长期维护同一个代码库的人。项目越大，收益越大。

### context7：治"自信的幻觉"的特效药

模型训练数据有截止日期，但框架没有。Vue、VitePress 这种迭代快的生态，模型凭记忆写出来的 API 经常是新版本里已经改掉的——最麻烦的不是报错，而是**它能跑但行为不对**。

context7 的作用就是实时拉取目标库当前版本的官方文档和示例。用法上没有技巧，属于"装上就自动受益"的类型。

### playwright：验证环节的自动化

改完前端代码，传统流程是：我打开浏览器 → 手动操作 → 截图贴给 Claude → 它再改。装了 playwright 之后变成：它自己开浏览器、自己点、自己看控制台报错。

说实话它不是必需品——手动验证也能做。但它的价值在于**闭环**：没有它，"改代码"和"验证效果"之间永远隔着一次人工操作，AI 的迭代轮次就上不去。

### arxiv：垂直场景的基建

搜索、摘要、全文下载、引用图谱。通用性不强，但如果你有论文阅读需求，它就是整个流水线的基础设施。我的论文从"发现"到"入库为结构化笔记"全程不碰鼠标，靠的就是它加几个自建 skill。

### bingcn：中文信息的补充信道

默认的 WebSearch 对中文内容覆盖一般，这个补上了国内博客、中文文档的检索。使用频率不高，但特定场景没有替代品。

## 二、插件：判断标准是"能不能形成肌肉记忆"

如果说 MCP 是扩展能力边界，插件（skill + hook + agent 的组合）就是固化工作方法。装插件的标准和 MCP 不同：**它得能变成不假思索的习惯，否则就是上下文负担**。

### 第一梯队：已经长在工作流里的

**superpowers**。严格说它是一个方法论框架：brainstorm → spec → plan → 实现 的完整链路，外加 TDD、调试等一系列经过验证的工作模式。这个知识库站点的几次大改动，设计文档都是在它的引导下产出的。它最大的价值是**强制你在写代码前把方案想清楚**——听起来简单，但 AI 编程最常见的浪费就是方向错了还在高速迭代。

**skill-creator**。Claude Code 的 skill 是"写一次、永久复用"的自动化资产，但写出能稳定触发的 skill 并不容易（描述写不好就不会被触发）。skill-creator 提供了创建、迭代、eval 评测的完整工具链。我的论文归档 skill 从 v1 到 v3 就是靠它的 eval 暴露出触发率问题的。

### 第二梯队：特定环节的把关者

**code-review**：提交前对 diff 做多维度审查，按置信度过滤后输出。价值不在发现问题多，而在它是"零成本的习惯"——不需要你记得去 review，它就在那。

**code-simplifier**：专改"能跑但丑"的代码。和 code-review 的区别是它直接动手精简，不只提意见。

**hookify**：思路很巧妙——分析历史会话，找出 Claude 反复犯错的行为模式，自动生成 hook 来拦截。相当于把"经验教训"从人的记忆转移到机制里。

### 第三梯队：理念认可，仍在观察

**self-improving-agent**：自动沉淀记忆、把经验提炼进 CLAUDE.md。方向是对的（AI 应该越用越懂你），但实际收益需要更长时间验证。

**llm-wiki**：Karpathy 提出的 LLM Wiki 模式的实现——用 AI 维护一个自我生长的知识库。和我现在"Obsidian + 人工整理"的路线理念相通但路径不同，留着观察两条路线的长期差异。

## 三、工具之间的真实关系

单看每个工具意义不大，重要的是它们怎么串起来。我目前的协作结构：

```
arxiv MCP ──→ 论文下载 skill ──→ 归档 skill ──→ 知识提取 skill
                                      │
codegraph ────→ 网站代码维护          ├── MinerU（外部 API）做格式转换
playwright ───→ 改完自动开浏览器验证   │
superpowers ──→ 大改前先出设计文档 ────┘
```

两条主线：**论文流水线**（MCP + 自建 skill 的组合）和**站点维护**（codegraph 定位 + playwright 验证 + superpowers 把关方案）。插件里的 review/simplify 则横切在两条主线的提交环节。

## 四、如果重来一次，我的安装顺序

1. **先装 context7 和 codegraph**。一个是防幻觉，一个是提效率，两者都是"装上即受益"，零学习成本。
2. **跑一两周，记录你重复让 Claude 做的事**。这些重复动作就是自建 skill 的候选，也是选插件的依据。
3. **按需补 playwright 和垂直 MCP**（比如我的 arxiv）。这层的判断标准就是你有没有对应的固定场景。
4. **插件最后装，且只装能进日常流程的**。每多一个插件，每次会话的上下文就多一份固定开销。

最后一个反直觉的心得：**工具数量和效率不成正比，甚至成反比**。Claude Code 的能力上限不在工具多少，而在你能不能把少数几个工具组合成稳定的流程。五个用熟的工具，胜过十五个吃灰的。

---

*以上配置基于个人场景，你的最优解大概率不同。但"先跑起来、记录重复、按需补装"这个选型思路是通用的。*
